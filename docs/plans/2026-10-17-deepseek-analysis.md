# M3 第二阶段：DeepSeek 与自动分批整理

用户已指定 DeepSeek，KEY 稍后自行配置，之后再进行真实调用测试。继续按已确认的检索协议实现后端，前端后置。

## 实现约定

采用直接 HTTPS 调用官方 Chat Completions 的适配器，以 `deepseek-flash`、非思考模式和 JSON 输出整理文字。对比引入额外服务代理和通用多供应商 SDK，本阶段采用 Android 自带网络栈，避免增加服务端部署与泛化配置。模型不能访问仓储或工具，唯一输入由受控执行器构建。

执行器先取得供应商实际发送的完整请求体，再计算字节预算、摘要及 token 计量。DeepSeek 官方下载的 tokenizer 与公开模板支持 UTF-8 保守上界，但不能证明和线上封装精确一致，因此明确登记计量类型，响应实际用量再次检查；超界结果拒绝。不能把中英文字数比例当作硬上限，也不能隐藏供应商提示词成本。

密钥使用 Android Keystore 包装密钥与 AES-GCM 加密，保存在 noBackupFilesDir，独立于数据库和导出。配置、状态、替换和清除均有后端接口；密钥不写入源码、构建参数或 APK。开发机真实测试另从仓库外密钥文件读取，只有用户后续配置且显式运行测试时才联网。

自动处理器沿分页目录枚举全部范围，逐字段选择未完成片段，每批一段，固定幂等标识；保存的调用台账就是恢复依据。限制单次执行批数，支持取消、失败后停止及显式恢复。附件、未知时间和不可读取文字继续列为缺口。所有输出仍为待核对提案，正式发布和画像不由本阶段擅自开启。

## 验证与后续依赖

模拟网络验证精确请求体、Bearer 认证、JSON 校验、截断、鉴权／限流／服务错误、超时、响应大小及 token 对账；不自动重试付费请求，不跟随重定向。模拟密钥验证加密保存、损坏失败与替换；自动处理验证长记录、恢复、预算和缺口。运行全仓测试、lint、APK 构建，新增需显式启用的合成资料真实调用测试。

真实 DeepSeek 请求、线上计量对账与模型质量在用户配置 KEY 后验证。Android Keystore 和实际联网仍需实体手机验证。研究依据见[DeepSeek 接入核验](../research/2026-10-17-deepseek-integration.md)。
