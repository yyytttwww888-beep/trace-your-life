# 分析质量验收

本文件区分程序能确定的可靠性与模型需要评估的语义质量。构建成功、请求成功、原文核对通过，分别证明不同环节；不能合并成“分析一定正确”。协议依据见[检索与可靠性](superpowers/specs/2026-10-16-knowledge-routing-and-reliability-design.md)，行动流程见[行动周期分析](ACTION_PERIOD_REFLECTION.md)。

## 已接入的程序门槛

来源枚举、修订与删除检查、每次实际发送的引用、输入和累计预算、跨批覆盖、明确确认、最新核对以及发布条件由程序执行。模型不能跳过这些检查，也不能自报统计分母。当前自动测试使用真实 SQLite 与合成资料、脚本化模型响应，检查成功和失败流程；它们没有测量 DeepSeek 的准确率。

新增的 DeepSeek 逐项核对协议验证检查片段完整覆盖原目标，并将非支持项、阻断性未知与整体意见做一致性约束。它用于阻止“理由已发现错误却仍整体支持”，不是自然语言真值证明。实现边界见[核对接口](CLAIM_REVIEW.md)，本轮各次失败、修复和独立复评见[日常知识库质量评审](reviews/2026-10-20-complete-daily-knowledge-quality-review.md)。

本轮对应行为测试：

| 入口 | 检查什么 | 不证明什么 |
| --- | --- | --- |
| `ActionReflectionWorkflowTest` | 生成与归并共享请求额度；完整输入才可确认；扫描与最终核对可分轮继续；明确反例、不支持、失败、来源变化及归档均不能误发布 | 真实模型每次都识别反例或正确判断相关性 |
| `ActionReflectionActivityTest` | 计划、回看的旧计划与下一轮计划分开；执行未知不显示未完成；原文可查；否定和选择可恢复；保存后进入知识详情 | 所有 Android 厂商设备行为与长期个人使用效果 |
| `KnowledgeDiscoveryTest` | 长文末尾、模板回答与经验说明能查到；分页不重复；修改与删除拒绝旧游标；失效内容明确区分；推荐不暗中改分类或关系 | 文本匹配能理解所有同义表达，或推荐一定语义相关 |
| `KnowledgeContextTest` | 已保存知识、经验、采用画像作为受控背景；本期原文与行动凭据独立引用；纠正、撤回、删除和备份恢复沿背景依赖传播；完整供应商输入预算与伪引用拒绝 | 带入背景后一定产生新见解，或行动自述已经成为客观执行测量 |
| 原有 `ActionPeriodReflectionTest`、`ActionPeriodReductionTest` | 固定计划与回看时间口径、完整来源扫描、删除与恢复传播，以及预算边界 | 用户回看已成为客观测量，或两个模型意见一致就是真值 |

具体运行数量与通过结果统一记录在[开发与验证](DEVELOPMENT.md)，独立语义评审保留对应运行身份及样本边界；本表不替代运行记录。

## 固定合成验收集合

语义检查必须保留输入与预期限制，不能只拿输出“读起来顺不顺”作为评价。以下内容均为虚构场景，适合逐项加入经显式授权的真实模型回归；每次只给某个固定范围，执行仍走正式受控接口，不把评估资料直接绕过预算拼入请求。

| 场景 | 合成输入设计 | 必须保留的区分或反例 | 不允许发布的判断 |
| --- | --- | --- | --- |
| 只有计划 | 期初写“每天练习十分钟”，本期没有回看 | 有计划；执行未知 | “这周完成了七次练习”或“未完成计划” |
| 明确未知 | 回看写“记得打开过练习，是否完成不清楚” | `UNKNOWN` 是执行自述；缺少实际过程 | “已执行”“未执行”或由此计算完成率 |
| 原计划与新计划 | 旧计划二十分钟；自述未执行；调整为五分钟 | 本期观察针对二十分钟，新计划尚无效果资料 | “五分钟的做法已经有效” |
| 非因果改善 | 一次小练习启动更快，同时难度下降、可用时间增加 | 至少保留难度、时间两种替代解释 | “先动手导致效率提升”或稳定性格判断 |
| 末尾反例 | 长记录开头支持做法，最后一段写失败情境 | 原文所有字段与末尾片段都参与处理；核对可见反例 | 只引用开头支持，忽略结尾后发布总体结论 |
| 跨周纠正 | 第一周判断被用户纠正；下一周出现相似表述 | 旧判断不是新事实；明确检查纠正是否仍适用 | 静默重复已否定的解释，或拿纠正编号当原文依据 |
| 同一经历重复总结 | 同一次练习先随记、再复盘、再产生摘要 | 同源材料不等于三个独立实验 | “三次实验都证明有效” |
| 缺失周期 | 七天只有两条回看；另外五天未记录 | 资料覆盖与生活覆盖不同，缺失仍未知 | 把记录缺失写成退步、失败或不自律 |
| 变化中的条件 | 简单任务先做有效；复杂任务先明确接口有效；第三周有例外 | 情境、反例、收窄范围和暂不能比较的部分 | “你总是适合先动手”或“复杂任务必须先设计” |
| 行动未被采纳 | 分析建议下周实验，但用户没有保存行动 | 建议与明确计划分开 | 下周复盘时宣称用户承诺或未完成这一建议 |
| 资料发生修正 | 请求期间修订执行状态，或删除其来源 | 拒绝旧写回，已保存内容退出当前有效视图 | 使用旧版本发布，或从历史备份恢复被删除的机器内容 |
| 建议是否有帮助 | 建议写清触发、做法、观察信号；后续用户自行记录回看 | “可执行的建议”与“实际有帮助”分开 | 因建议被保存或语言积极就算已改善 |

每个场景先确定预期，再运行。不能为了让测试通过而把预期改为本次模型输出；若预期本身有问题，保留修订原因及先前结果。

### 可执行固定案例 v1

[`SyntheticQualityCases`](../app/src/test/java/dev/tracelife/quality/SyntheticQualityCases.kt) 固定六组虚构原文、绝对日期、提问、必须保留的区别、禁止结论与新增价值要求：同一经历重复总结、长文末尾反例、缺失周期、历史纠正、计划与执行、新条件相对已有理解。历史纠正案例先通过正式台账保存脚本化旧判断和独立纠正，新问题只分析后来的原文；旧判断不算新的来源。

[`DeepSeekKnowledgeQualityLiveTest`](../app/src/test/java/dev/tracelife/quality/DeepSeekKnowledgeQualityLiveTest.kt) 通过正式对话入口执行这些案例，默认跳过。最新验收扩展到每条发现的真实原文核对与正式发布尝试：每例最多 3 次生成／导航及 6 次核对，全套最多 54 次真实请求，不自动重试失败案例。输入和预期保持 v1 不变，结果不得反向改变案例。生成阶段检查范围覆盖、完整原文处理、预算、引用归属、历史意见读取及没有自动发布；随后模拟明确确认与历史人工对照，重读原文核对并尝试正式发布。模拟确认特意不代表人已判对，核对仍须独立承担检查。非支持意见被门禁正确挡住属于程序通过；SUPPORTED 或成功发布不自动等于语义正确。例中有足够明确的材料，完全没有发现会作为用处不足的失败保留。所有失败仍计入六例分母，不以“出现某个词”代替语义判定。

```bash
./gradlew testDebugUnitTest \
  --tests 'dev.tracelife.quality.DeepSeekKnowledgeQualityLiveTest' \
  -PtraceLifeDeepSeekQuality=true \
  -PtraceLifeQualityReportDir="$HOME/Library/Caches/trace-life-tools/quality"
```

密钥仍从仓库外的既有配置文件读取，不进入参数、报告或 APK。每次在报告目录下创建独立子目录，写入 `report.json`、`report.md` 及仅含合成内容的请求和成功响应；不写请求头或密钥。报告保留模型、适配器、固定日期、预算、实际调用次数、覆盖、耗时、生成结果与错误类别。来源列表表示该发现可下钻的生成上下文；精确引用与回答文字应对照同目录请求／响应，不能仅因上下文里存在某条原文就判引用支持。

自动报告中的语义项标为待独立评审。检查者须对照本节后述六个语义标签，以及每例固定的区别／禁止结论／新增价值要求，记录“符合／有问题／资料不足”及输出位置。程序测试通过不会把这些语义项自动改成符合；未运行原文核对或未发布也明确保留。实际运行结果及人工评审记录写入[开发与验证](DEVELOPMENT.md)，不从代码存在推断测试已执行。

报告的 `finalOriginalReviews` 逐项保留固定目标、真实意见、问题标签、支持／反例引用、核对未知项和实际发布结果。生成的 `unknowns` 不属于知识发布的独立目标，仍须对照原文和正文作独立语义评审；不能用正文经过核对宣称整份回答没有矛盾。

[`DeepSeekSemanticGuardLiveTest`](../app/src/test/java/dev/tracelife/quality/DeepSeekSemanticGuardLiveTest.kt) 是另一个固定的真实核对挑战集：九条故意错误的目标涉及明确未执行、时长／等待、事件内次数、比较基线、因果升级、长期稳定、已知重复、计划／回看重复计数，以及“局部错误事实加保守结尾”，另加两条合理有限的对照描述。`authored-semantic-targets-v2` 保留 v1 的原十例及预期，只新增不同情境的步骤顺序混淆负例，旧报告不覆盖。原文和目标由测试作者预先固定，不调用模型生成；每例只作一次真实核对，再尝试正式发布。错误不能获 SUPPORTED／发布，合理对照需受支持，防止“全部拒绝”冒充正确。每轮最多 11 次请求，与上方同时运行最多 65 次；使用同一显式 `traceLifeDeepSeekQuality=true`，默认跳过。全部请求及失败另存报告，不覆盖之前生成案例或两轮评审。

```bash
./gradlew testDebugUnitTest \
  --tests 'dev.tracelife.quality.DeepSeekSemanticGuardLiveTest' \
  -PtraceLifeDeepSeekQuality=true \
  -PtraceLifeQualityReportDir="$HOME/Library/Caches/trace-life-tools/quality"
```

生成、归并、普通及行动核对共用 `SemanticQualityGuidance`：检查对象／事件／日期／数值单位、明确否定与缺失区别、历史背景边界、比较基线、同现与因果、局部重复与长期稳定、行动启动和完成信号，并让未知项与正文相互对照。处理覆盖由程序展示，不从分片形式臆造“原文未完整提供”。这些约束是可评估的提示改进，不替代原文核对或用户判断，也不能单独证明语义问题已经消失。 DeepSeek 核对另外采用程序强制的 `review-checks-v2`：程序无损划分目标原文，检查须按序覆盖每个固定段号且恰好一次，引用须属于本次输入；局部非支持、阻断未知及问题标签不能被整体 `SUPPORTED` 绕过，理由归一保留到既有核对记录。模型仍可能错误地把某段标为支持，完整文本覆盖不代表真正逐逻辑事实理解正确，须继续独立评审。格式、上限和旧任务身份兼容见 [DeepSeek 接口](DEEPSEEK.md#预算与响应校验)。

[2026-10-20 两轮独立评审](reviews/2026-10-20-integrated-knowledge-quality-review.md)并列保留首次问题和修复后的实际结果，包括计划／时长表达、事件单位、整体归并的过期未知项，以及仍出现的缺口误报、背景混入和因果升级；不合成全通过或准确率结论。

### 长期规模与预算验收

[`LongTermConversationScaleTest`](../app/src/test/java/dev/tracelife/quality/LongTermConversationScaleTest.kt) 使用真实 SQLite、正式对话编排与 DeepSeek 完整请求计量，模型响应为脚本化合成内容，运行不联网：

- 365 个连续日期，其中部分记录未分类。分页目录逐项核对无遗漏、无重复；每轮最多 5 次请求，重新打开库后继续，直到全部原文与跨批归并完成。检查全部来源链和默认任务总预算，完成后再次点击不重复请求。
- 含非 BMP 字符、超过一万 Unicode 码点的长文。核对片段边界连续、首尾完整、最后反例实际进入请求；归并只接收有来源的草稿，不能偷偷重传全部原文。
- 同样的全年资料只允许两次请求。额度用完时保留真实缺口并禁止保存，重启或重复继续均不得再发送或伪装成完成。

报告记录每轮请求数、原文／归并数量、实际完整输入字节与保守 token 计量、累计预算、分页数和耗时。耗时用 `System.nanoTime()` 测量，包含本次执行开销，不设依赖测试机速度的通过阈值。短日记一年的成功不代表任意长文、附件、复杂已有背景或全部长期库都能在相同预算内完成；脚本化响应也不证明模型能理解一年经历。

```bash
./gradlew testDebugUnitTest --tests 'dev.tracelife.quality.LongTermConversationScaleTest'
```

## 每次真实检查的记录口径

结果保存到仓库外，使用合成资料。记录案例版本、任务绝对日期范围、模型及适配器版本、配置预算、请求数量、来源覆盖、最后核对和是否实际发布；API KEY 不进入记录。仅在需要定位错误时保存合成请求或输出，禁止记录 Authorization 等凭据字段。

程序检查分别记录：引用归属是否通过、完整输入是否覆盖、统计与口径是否一致、快照是否仍有效、错误状态是否阻止发布。接口解析失败应记为失败，不自动从“质量评估分母”消失。

人工语义检查采用独立标签，可在同一输出中同时出现：

- 引用支持：关键说法能否由引用的原文支持，是否把计划、自述、测量混为一谈。
- 反例保留：预设的重要反例是否被提到，是否影响最终表述或继续保存的决定。
- 范围适当：是否从一次经历推断长期倾向，从部分记录概括全部生活，或把相关写成因果。
- 历史一致：是否正确处理旧纠正与否定；有新证据时是否说明重新考虑的条件。
- 新增价值：是否只是重复既有描述，还是指出新的条件、例外、变化或可验证的问题。
- 行动可用：是否给出可尝试的具体步骤和观察信号；是否承认目前无法判断效果。

每项使用“符合／有问题／资料不足”，附问题对应的输出和依据位置，不合成一个个人成长分。报告分母必须是实际运行的案例与请求；调用失败、无法评价、未核对或未保存单独报告。单轮全部符合只能说明这些合成案例，没有覆盖未知场景。

## 长期检查与当前边界

同一套固定案例在提示、模型、检索或发布逻辑变化后按受影响维度复测；新增失败案例加入固定集合。对重复性和随机性的判断需要相同案例多轮结果，不能用单次成功替代。一般回归测试默认不联网，不因为运行测试而自动消耗用户额度。

“建议实际有帮助”需要后续真实执行与用户回看，不能在生成时评价。未来可以在行动回看中收集独立的帮助程度与原因，但必须由用户自述，保留未执行、未知及外部条件；本轮没有自动进行效果归因或长期模型评分。实体手机验收、华为健康接入和长期个人资料效果仍以实际验证记录为准。
